## 2. ESL protocol design and lifecycle

**Framing** (`esl.py`): messages are `\n\n`-terminated header blocks plus an optional `Content-Length` body.

| Rule | Behaviour |
|---|---|
| Header block | At most 8 KiB, strict UTF-8, every line must be `name: value`; duplicate `Content-Type`/`Content-Length` rejected |
| Body | `Content-Length` must be ASCII digits (`+5`, `-5`, `abc` rejected), at most 64 KiB; read until complete |
| `api/response` | `Content-Length` required; body starting with `-ERR` is a protocol error |
| `command/reply` to an `api` | `-ERR permission denied` (what FreeSWITCH 1.10.12 sends for a disallowed API) is an `auth` error; anything else is a protocol error |
| `text/disconnect-notice` | Treated as connection loss at any point (greeting, auth, command), before any body is read |
| Extra bytes after a complete response | Protocol error (one request is outstanding at a time) |
| Reads | Each message must complete within one `read_timeout` (slow-drip is bounded), and within the run deadline; partial reads and writes are handled |

**Run deadline:** `min(connect_timeout + 2 × read_timeout, 0.9 × min_collection_interval)`. With defaults that is 9 s against a 15 s interval.

**Lifecycle per run**

1. A connected, non-stale connection is reused. Staleness is checked with a zero-timeout `select` (peer closed or sent unsolicited data).
2. If the reused connection fails with any operational error except `auth`, exactly one fresh connection is attempted in the same run.
3. A connection that is new in this run and fails is **not** retried. There are no loops: at most 2 connection attempts per run.
4. Any error in the client closes the socket and clears the buffer (no reuse of a possibly desynchronised stream). A parse error on an in-sync connection leaves it open and the next attempt reconnects anyway.
5. Unexpected exceptions (not `EslError`) discard the connection and propagate to the Agent. Only expected operational errors are caught.

**Command safety:** `ALLOWED_COMMANDS = {'uptime s', 'show channels count'}`, exact match enforced inside `EslClient.api()`. Everything else, including CR/LF variants, case variants and trailing spaces, raises `EslCommandNotAllowed` before anything is sent. No events, no `bgapi`, no `exit` command (the socket is just closed).

**Error taxonomy** (`error_type` tag): `connect` (refused, unresolvable, closed or lost, disconnect notice, truncated body), `timeout`, `auth` (rejected credentials or permission denied), `protocol` (framing, wrong type, `-ERR`, extra data), `parse` (well-formed reply but not a number or `N total.`).

## 3. Authentication and `userauth`

- No `username`: sends `auth <password>`.
- `username` set: sends `userauth <user@domain>:<password>`. **There is no fallback** to `auth`; a rejected `userauth` ends the run with `error_type:auth` and no second authentication attempt (tested).
- Syntax and framing checked against `mod_event_socket.c` from FreeSWITCH **v1.10.12** (GitHub tag, fetched into a scratch directory, not the Dockerfile's tarball). Facts used:
  - `userauth` splits at the first `@`, then at the first `:`; the user part must not contain `:`, the domain must not be empty.
  - Failure replies `Reply-Text: -ERR invalid` and the connection is closed.
  - Success replies `Reply-Text: +OK accepted` with extra `Allowed-Events`, `Allowed-API`, `Allowed-LOG` headers.
  - `esl-allowed-api` is matched on the **first word** of the command (`uptime`, `show`).
- Client-side validation (before connecting, as `ConfigurationError` with fixed text): username must match `user@domain` with no whitespace, `@` or `:` inside parts; password must be non-empty with no control characters.

**Unresolved limitations**

1. `userauth` was **never run against a real FreeSWITCH**. The lab has no directory users, and creating one needs a separate approved lab change. Tests use the fake server, which implements the documented reply shape.
2. A `userauth` user with no `esl-allowed-api` receives `Allowed-API: all`, i.e. full API access. The check does not inspect that header and does not refuse such a user. Doing so would be a stricter policy than the brief asked for; it is a candidate for Milestone 4.
3. The shared-password mode grants full control; this is documented in the README and spec.
4. ESL is plaintext TCP; no TLS exists in 1.10.12.

## 5. Security protections and tested failure paths

| Protection | How it is verified |
|---|---|
| Password never in logs, exceptions, tags, `repr` | Sentinel password; hostile server that echoes it in auth reply, `-ERR` body, garbage body and a bad header; asserts on `caplog` (DEBUG), exception `str`/`repr`/`args`, `__cause__`/`__context__`, all metric tags, `repr(check)`, `repr(client)` |
| Only allowlisted commands sent | 21 rejected command strings including every one listed in the brief and CR/LF injections; server transcript shows zero `api` lines; over 10 runs the server only sees `auth`, `api uptime s`, `api show channels count` |
| No subprocess or shell | `subprocess.Popen/run`, `os.system/popen/execv/posix_spawn` monkeypatched to fail; source scan for `subprocess`, `os.environ`, `getenv`, `threading` |
| No threads | Thread set identical before and after repeated runs |
| No retry loop | Server dropping reused and new connections: exactly 2 connections in that run, 1 in the next |
| No credentials to a non-ESL peer | Wrong greeting: nothing is sent |
| Bounded resources | 200 runs: 1 connection, 400 commands, empty buffer, no new tag sets or threads |
| No cross-instance leakage | Two instances with different passwords; each fake server sees only its own |

Tested failure paths (all pass): invalid password; rejected `userauth` with no fallback; permission denied; connection refused; unresolvable host; disconnect during auth and during a command; `text/disconnect-notice` in greeting and mid-command; restart between runs (transparent reconnect, `can_connect` stays 1, errors 0); connection dying mid-exchange (replaced in the same run); recovery after failure; no greeting; stall in auth; stall in command; slow drip; run deadline under a 1 s interval; missing, negative, signed, non-numeric, huge, oversized and duplicate `Content-Length`; truncated body (closed and stalled); wrong or missing content type; malformed and non-UTF-8 headers; unknown command; unexpected reply; extra frame; header 9000 bytes with and without terminator; 70000-byte body; late reply after a timeout cannot corrupt a later run; 16 unparseable-body variants.

## 7. Lab verification (read-only)

State before: container `healthy`, uptime hours, idle. No config, ACL, secret, image or baseline file changed; `git status` of the lab shows only the earlier untracked report.

**Method.** The ESL port is not published and `docker exec` is the only path that needs no lab change. A throwaway host script listened on a random `127.0.0.1` port and, per connection, ran `docker exec -i <container> python3 -c <relay>`, a 15-line byte pump to `127.0.0.1:8021` inside the container (inside the ACL). The **real `FreeswitchCheck`** (hatch test env, Python 3.13) ran on the host against that port and read the shared password in-process from the ignored `secrets/esl_password` file (never printed). The check polled every ~0.5 s while the existing harness ran `scripts/run-call-load.sh --scenario normal --calls N --hold 10` (`--allow-high` for N=10); all three runs finished "as expected".
