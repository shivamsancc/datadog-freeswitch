## 4. Sessions, channels, legs, calls: what the evidence supports

### 4.1 The numbers

All **derived** from the saved samples.

Steady-state values, `show channels count` (baseline), `status` first number (baseline), `show calls count` (baseline):

| Harness calls | channels | sessions (`status`) | `show calls` rows | `sessions_since_startup` increase |
|---|---|---|---|---|
| 0 | 0 | 0 | 0 | 0 |
| 1 | 4 | 4 | 3 | 4 (run `20261011T140335Z`, `20261011T141015Z`) |
| 5 | 20 | 20 | 15 | 20 |
| 10 | 40 | 40 | 30 | 40 |
| 3 (`timeout`, `ALLOTTED_TIMEOUT`) | 12 peak | 12 peak | 9 peak | 12 |
| 3 (`fail`, `NO_ROUTE_DESTINATION`) | **0 peak** | **0 peak** | **0 peak** | **6** (derived: 2 per failed attempt) |

Across all 172 one-second samples (172 reads, each of three separate commands):

- `sessions_current == total_channels` in **165** samples; in **7** it did not
  (for example sessions 16 vs channels 12, sessions 24 vs channels 28, sessions 4 vs channels 6 or 8). All 7 are during
  call setup or teardown of the 5- and 10-call scenarios. Of the 172 samples, 171 had `show_calls_rows` equal to
  three quarters of `total_channels`; the one exception was 6 channels with 5 rows (a transitional sample). Because
  `show calls` is a third separate read, an exact 3:4 relationship is a property of settled loopback calls only.
- `lab_legs` (channels whose UUID starts with `lab-`, that is the harness's near leg) was always exactly
  `channels / 4`, and `loopback_channels` equalled `total_channels` in every sample: **every channel in these runs was a
  loopback channel**.

### 4.2 Interpretation

| Concept | Lab evidence | Status |
|---|---|---|
| **Channel** | A row in `show channels`; counted by `show channels count` | OBSERVED |
| **Session** | `status` "N session(s)". Equal to channels at steady state | OBSERVED (equality), INFERENCE (that a session is the core object that owns one channel) |
| **Leg** | A channel is one leg of a call. One harness call has 4 legs: the near leg (`lab-…`), its loopback partner, and the far loopback pair. Mapping taken from `esl-load` (`originate {…}loopback/<near>/default &bridge(loopback/<far>/default)`), **not** from saved rows | INFERENCE from source of the harness |
| **Logical call** | Not observable. The harness knows it started N calls (`load.json` `counters.initiated`); FreeSWITCH reports nothing named "calls" | UNVERIFIED as a server-side count |
| **Bridged call** | `show calls` rows are 3 per harness call. One bridge exists in the harness (near leg to far loopback). Why there are 3 rows and not 1 is **unexplained** by existing artifacts | UNRESOLVED |

### 4.3 Do sessions and channels differ?

- **At rest, no difference was observed** in 165 samples and in every steady-state baseline series.
- **They are not the same quantity by construction**, because they are read from two different commands at slightly
  different times, and the 7 transitional mismatches show both can lead and lag. The evidence cannot separate
  "non-atomic reads" from "the two objects have different lifetimes".
- **Counters diverge from channel visibility.** A failed originate (`NO_ROUTE_DESTINATION`) raised
  `sessions_since_startup` by 2 per attempt while the channel table was never seen non-empty at 1 s sampling. So
  sessions are consumed by attempts that the `show channels` poll can miss entirely. This matters for **rate** metrics,
  not for a gauge of current concurrency.
- `sessions_current == channels` equality **holds in a loopback-only lab**. Whether it holds with SIP endpoints, `park`ed
  inbound legs, conference or `mod_callcenter`-style members, or hung-up channels held for post-processing is
  **UNVERIFIED** (no such call was ever generated).

**Conclusion for `sessions.active`.** Collecting `sessions.active` today would add a second, nearly identical gauge
(always equal at rest, transiently different by up to 33% of the value in the 7 transitional samples). That fails the
roadmap's "no duplicate measurements" principle unless a divergence at rest is demonstrated with SIP calls. See
[§8](#8-recommendations-for-the-metric-contract).

### 6.2 Version

- `version` (long form) is OBSERVED and gives the version string.
- `version short` is **not evidenced anywhere**. Its output must not be assumed to be `1.10.12`.
- The version is also recoverable without a new command: the `status` banner contains the same version in parentheses
  (OBSERVED). If `status` is ever added, the version may be obtainable from it at no extra command; this is a design
  option, **not** a recommendation to add `status` (that remains Q-1).

## 7. Verified facts, inferences and open questions

### 7.1 Verified (OBSERVED)

1. FreeSWITCH is 1.10.12; `show channels count` returns `\n<N> total.\n`; the existing parser's regex matches that shape.
2. One harness (loopback) call is **4 channels**; `show channels count` and `status` current sessions both read 4/20/40
   for 1/5/10 calls over 45-query series with no variation.
3. `show calls count` reads **3 per harness call** (0/3/15/30).
4. `status` contains parseable lines for current sessions with peak, sessions since startup, max sessions and per-second
   limit; max sessions is 200 and sessions-per-second is 30, matching configuration.
5. `sessions_since_startup` increases by 4 per completed or timed-out harness call and by 2 per failed attempt. It was
   seen to fall to a low value between some runs; that this was a FreeSWITCH restart is **inferred** (the M4 report
   documents one container start; the other resets are not documented).
6. A failed (`NO_ROUTE_DESTINATION`) attempt creates sessions that a 1 Hz channel poll did not observe.
7. During setup and teardown, `status` sessions and `show channels` rows briefly disagree (7 of 172 samples).
8. The lab cannot produce a registration, a gateway state, or a non-loopback call in its current configuration.
9. `version` is available; `version short`, `show registrations`, `show bridged_calls count` have **no** evidence.

### 7.2 Inferences (may be wrong)

1. A session maps one-to-one to a channel at rest. (True in the lab; not shown with SIP.)
2. A real SIP bridged call is 2 channels and 1 `show calls` row. (Only because the audit says "typically 2".)
3. The 4-channel loopback structure is two loopback pairs as the harness script constructs it.
4. The 3 `show calls` rows per call are artifacts of loopback legs; the 2 sessions per failed attempt are the near
   leg plus its loopback partner.
5. `peak` is a high-water mark that survives at least the observed window.

### 13.4 Verified facts, inferences, unresolved

**Verified (observed in saved artifacts or in code)**

1. L1 allows exactly `uptime s` and `show channels count`; `status`, `show channels`, `version` and others are
   rejected before sending, and tests lock this.
2. L2 refuses any `userauth` account whose advertised `Allowed-API` is not exactly {`uptime`, `show`}, including a
   superset such as `uptime,show,status`, and does not apply in shared-password mode.
3. The `check` run budget is computed as `min(connect_timeout + 2 * read_timeout, 0.9 * interval)`: it **assumes two
   commands** (one connect, two replies).
4. Any `-ERR` reply or malformed reply is raised as an error that fails the whole run (`can_connect` 0, no gauges), so
   an optional command that is unsupported on some version would currently take the existing metrics down with it.
5. M4 (live, restricted temporary user): `uptime s`, `show channels count` and `show channels` allowed; `version`,
   `status`, `global_getvar`, `eval` and `bgapi version` denied by the server.
6. The inventory contains the three candidates with the syntax quoted in §13.2, and `sofia`, `sofia_count_reg` and
   `sofia_gateway_data` are three separate rows.
7. `esl-check` has no command restriction and uses the shared password.

**Inferred (may be wrong)**

1. `show status` is permitted for a `uptime,show` account (first word `show`).
2. Permitting `sofia` would not permit `sofia_count_reg` or `sofia_gateway_data`, and the reverse, because matching is
   on the whole first word. The M4 results are consistent with this but do not prove it (see U-S1).

| `N session(s)` | 0 | 4 | 0 | 0 | Current sessions; equals channels in every sample |
| `since startup` | 0 | 4 | 4 | 4 | Counter. +4 for one call. **Does not decay** |
| sessions line `peak` | 0 | 4 | 4 | **4** | Held at 4 for at least 5 min 35 s after the last session ended |
| sessions line `last 5min` | 0 | 4 | 4 | **0** | Rose with the call; still 4 at +1 s; **0 at +5 min 35 s** |
| per-sec line current | 0 | 0 | 0 | 0 | Instantaneous rate; 0 at each sample (the 4 sessions were created in one second, before the first sample) |
| per-sec line `peak` | 0 | 4 | 4 | **4** | Held for at least 5 min 35 s |
| per-sec line `last 5min` | 0 | 4 | **0** | 0 | **Fell to 0 between +4 s after start and +32 s after start**, i.e. well inside 5 minutes |

What this does establish:

1. **`peak` and `last 5min` on the same line are different quantities.** At +5 min 35 s the line read
   `0 session(s) - peak 4, last 5min 0`. So `peak` is **not** the five-minute window.
2. **`peak` did not decline during an observation of 5 min 35 s.** That is consistent with an all-time-since-start
   high-water mark (or a window longer than 5.6 min). **It does not prove all-time**, and it does not prove a rolling
   window. The semantics of `peak` remain **inconclusive** for the reasons in the task statement.
3. **`last 5min` on the sessions line decayed to 0 only after about 5 minutes**, consistent with a five-minute lookback.
   The data bound the transition to between 1 s and 5 min 35 s after the call ended; **the exact 300 s boundary was
   not observed**.
4. **`since startup` is a monotonic counter of sessions created**, +4 per harness call in every observation.

What it does **not** establish, preserved as unresolved:

- **What `last 5min` is** (a maximum, a mean, a sampled bucket). The sessions-line value behaved like a five-minute
  lookback, but the **per-second line's `last 5min` dropped to 0 within about 30 s** of the burst while the same
  burst remained in the sessions-line `last 5min` and in both `peak` values. The two `last 5min` fields therefore do
  **not** follow one common rule that can be stated from this evidence.
- Whether `peak` resets on a restart (previously seen) is irrelevant here; whether it can be reset without a restart
  is unobserved (the `fsctl ... sps_peak_reset` entry in the inventory hints that it can, not that it was exercised).
- Behavior for multiple calls, failed originates, overlapping bursts, or after 5-minute boundaries relative to
  several bursts.
- The meaning of `min idle cpu` (it varied 98.60 to 99.50 across samples) and `Current Stack Size/Max`
  (constant `240K/8192K`).

#### 13.10.7 Other observations and caveats

- **Timestamp offset (unexplained).** The `created` and `created_epoch` values of the four channels were about
  6,254 s (about 1 h 44 min) **earlier** than the harness's own wall-clock start epoch of the same call. The harness
  clock agrees with `uptime s`. Do not use `created*` fields for timing or alerting until this is explained; no
  cause is established here. (An earlier note in §12.2 already recorded an unexplained gap between container uptime
  and FreeSWITCH uptime.)
- **Sampling skew was not seen:** sessions equaled channels at the only loaded sample. The 7 mismatches found in the
  2026-10-11 data (§4.1) occurred during setup and teardown, which this session did not sample.
- **One call only.** This is not a benchmark and does not represent production behavior. Loopback calls use L16
  at 8 kHz inside FreeSWITCH, so these samples say nothing about RTP, codecs on the wire or voice quality.
- The `show channels` and `show calls` bodies contain fields (UUIDs, caller name and number placeholders,
  addresses, container hostname) that would be sensitive on a real system. They are sized (1.2 to 1.6 KiB here) but
  scale with call count, so any use needs row caps and redaction (gate G8, §13.7).

### 14.7 Raw ESL driver specification (to be implemented and reviewed)

**The driver source does not exist.** The Milestone 4 driver was a throwaway and was not preserved. It must be
written, tested offline and independently reviewed (G-C1) before Session C. This section is the specification a
reviewer checks it against. It is derived from the tested behavior of `esl.py` (`_connect_and_auth`, `api`,
`_read_message`) and its tests; the driver reuses **no** secret-bearing helper.

| Area | Required behavior |
|---|---|
| Transport | One TCP connection to `127.0.0.1:8021` **from inside the container**; no other host or port; no listener; no subprocess; stdlib only |
| Input | The temporary credential (`user@domain` and secret) is read from **stdin** only; the command list is a **hardcoded tuple** in the source equal to §14.6.1; the secret never appears in `argv`, environment, logs or output |
| Handshake | Read one message; require `Content-Type: auth/request`; otherwise abort. Send exactly one line `userauth <user@domain>:<secret>` terminated by a blank line. Read one message; require `Content-Type: command/reply` |
| Auth result | `Reply-Text` starting `+OK` is success; anything else is a failure and the driver stops **without** falling back to `auth` and without sending any `api` line. The success headers `Allowed-API`, `Allowed-Events`, `Allowed-LOG` are recorded verbatim, including whitespace, with a note of any duplicate header |
| Pre-check | If `Allowed-API` is not exactly `uptime,show`, stop **before** sending any `api` line (the account was provisioned wrongly) |
| Queries | One `api <literal>` line per command from the tuple, sent only after the previous reply is fully read; a runtime assertion refuses any string not in the tuple, and any CR, LF or control character. No loops, no retries |
| Replies | Read one complete message per query. Headers are limited to 8 KiB and the body to 64 KiB (the client's limits); `Content-Length` must be a non-negative integer within bound; a body that is not UTF-8 is recorded as such. Unsolicited extra data after the reply is recorded and stops the run |
| Classification | Record `Content-Type`, `Reply-Text` (if present), body length, and an outcome label: `accepted` (`api/response`), `denied` (`command/reply` with `-ERR permission denied`), `unknown-command` (`api/response` with `-ERR ... Command not found!`), `protocol-error`, `timeout`, `closed`. The label for T-B and T-C is computed by the driver, not by a person |
| Deadlines | Per-message read timeout and a whole-session deadline (both fixed small values). Exceeding either aborts and cleans up |
| Cleanup | Close the socket in a `finally`; do not send `exit`; no further connection |
| Output | Only: command string, `Content-Type`, outcome label, `Reply-Text` truncated and with control characters removed, body length, and for **T-A and T-B only** the body (bounded and control-character-stripped). The secret and the full `userauth` line are never printed; exception messages are fixed text; a server body that contains the secret string causes the body to be withheld |
| Failure of the harness | Any unexpected exception prints only the exception **type** |

Offline tests required before review: success path; denial; wrong password; header variants (`all`, absent,
padding, duplicate); oversized header and body; malformed `Content-Length`; truncated reply; hostile server echoing
the secret; server sending an extra command-like line; a server that never replies; confirmation that no `api` line
is ever sent for a string outside the tuple.

### 14.10 Cleanup, restoration and rollback

**Cleanup (always):**

1. Disconnect; confirm 0 channels.
2. Delete the one file the session created. Nothing else is deleted or edited.
3. `reloadxml` once.
4. Verify: `directory/` lists only `default.xml`; the SHA-256 and `stat` of every file equals the step-2 record.
5. Verify the temporary credential no longer works: the driver's `userauth` is answered `-ERR invalid` (M4 §8
   precedent). This is one extra connection and sends no `api` line.
6. Verify the lab: container healthy, restart count unchanged, health command passes, `show channels count` is
   `0 total.`.
7. Delete the secret file and any driver output that contained headers; keep sanitized results only in this report.
8. Search the repositories and scratch directories for the temporary user id and domain; expect none.
9. `git status` shows no change attributable to the session.

**Rollback conditions and actions:**

| Condition | Action |
|---|---|
| A preflight gate fails | Stop. Nothing was changed |
| File creation or `reloadxml` fails or returns an error | Delete the file; `reloadxml`; verify hashes |
| After the first reload the health check fails or the container is unhealthy | Cleanup steps 2 to 6 immediately. **No restart** |
| T-C is accepted, or `Allowed-API` is not exactly `uptime,show` | Stop querying; cleanup |
| A file other than the temporary one differs from the record | **Do not overwrite it.** Report it. It was changed by something other than this session |
| The temporary user still authenticates after removal | Repeat deletion and reload once; if it persists, report a failed rollback and stop |

**Limitations of this rollback:**

- It removes what the session created; it cannot undo a side effect of the reload itself whose existence is unknown
  (§14.4). Detection relies on behavioral post-checks only.
- It does not restart FreeSWITCH, and **no restart is part of any rollback**. If the lab is left in a state the
  checks flag, the response is to stop and report, and a restart needs its own approval.
- If the host or Docker is interrupted mid-run, the cleanup list above must be run manually from the step-2 record;
  the temporary file may remain on disk with a live secret in a **tracked tree**, so interruption handling is the
  highest priority of the runbook (§14.12).

### 14.12 Backup and secrets handling (review D)

- **Backup is a record, not an archive.** The session adds one file and removes it. The 12 configuration files are
  tracked in Git (and equal the M4 hash record), so the restoration source already exists. A hash-and-`stat` record is
  sufficient to detect an unexpected change; a full archive would add a second copy of configuration with no recovery
  benefit and is dropped. The M4 hash record is used only as an independent comparison and is neither modified nor
  overwritten.
- **Restore only what the session changed.** The only change is the one created file. Files that differ from the
  record are reported, never overwritten.
- **Locations.** Records and the secret live in a new mode-0700 directory outside every repository; the secret file is
  mode 0600. Nothing is written under a repository except the one temporary directory file, which is unavoidable
  because the bind mount source is inside the project tree.
- **Residual risk (stated, not hidden).** The temporary directory file contains the temporary secret and sits in a
  tracked directory of the working tree; it is untracked but **not** ignored by the repository's ignore rules. A
  careless `git add -A` during the window would stage it. Mitigations: keep the window short, never stage during it,
  remove the file first in any rollback, and verify with `git status` at the end. The secret is only valid while the
  file exists and the reload has been applied.
- **No credentials in Git-tracked documentation**; no printing of the secret in any log; passed to the driver on
  stdin only; the driver withholds any output that contains it.
