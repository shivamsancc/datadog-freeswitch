# datadog-freeswitch

Development lab for a future Datadog Agent integration for FreeSWITCH.

**Current milestone: 1 – FreeSWITCH Docker lab.** This repository currently contains only the
lab: a single, version-pinned FreeSWITCH container with an authenticated, private Event Socket
(ESL) endpoint. The Datadog check, collectors, dashboards and synthetic call generation come in
later milestones.

> **This is a development lab, not a production deployment recipe.** It is intentionally
> minimal, runs a stripped-down module set and ships no real SIP users or carrier connectivity.

## Why this image (and not a prebuilt one)

- There is no public, maintained prebuilt FreeSWITCH image. The upstream
  `signalwire/freeswitch` `docker/` Dockerfiles install from `freeswitch.signalwire.com`, which
  answers `401` without a SignalWire personal access token.
- This lab therefore builds **FreeSWITCH 1.10.12** (stable release series) from the public
  release tarball, verified by SHA-256, together with pinned **sofia-sip v1.13.17** and
  **spandsp v3.1.1** (the Debian bookworm packages are too old). Only the modules the lab needs
  are compiled (`docker/freeswitch/modules.conf`). No credentials are required.
- Base image: `debian:bookworm-slim` (tag-pinned, not digest-pinned). First build takes ~3 minutes.
  The FreeSWITCH process runs as the unprivileged `freeswitch` user (uid 999).

The future integration only needs ESL, so it works the same against Docker, package, source or
Ansible-managed FreeSWITCH installs; this lab is just a controlled target.

## Prerequisites

- Docker Engine with the Compose v2 plugin (file-based `secrets:`) (tested: Docker 29.6.2, Compose 5.3.1, Docker Desktop on arm64).
- `openssl` (used by `scripts/lab-up.sh` to generate the ESL password).
- Outbound internet access for the first build (GitHub, files.freeswitch.org, Debian mirrors).

## Quick start

```bash
scripts/lab-up.sh          # creates .env and secrets/esl_password (random) on first run, builds, starts, waits for healthy
scripts/verify-lab.sh      # runs the verification checks (add --call-test for one loopback call)
scripts/lab-down.sh        # stop and remove containers/network (keeps log/db volumes)
scripts/lab-down.sh --purge   # ... and delete the volumes
```

## Configuration and secrets

| File | Purpose |
|---|---|
| `secrets/esl_password` (git-ignored) | The ESL password. Generated by `scripts/lab-up.sh`; mounted into the container as the Docker secret `/run/secrets/esl_password`. |
| `.env` (git-ignored) | `LAB_SUBNET`, `HOST_BIND_ADDR`. No secrets. |
| `docker/freeswitch/conf/` | FreeSWITCH config, bind-mounted **read-only** at `/usr/local/freeswitch/conf`. Version-controlled, contains no secrets. |
| `docker/freeswitch/modules.conf` | Build-time module selection. |
| `docker/freeswitch/bin/` | `esl-check` (stdlib Python ESL client used by the health check) and `fs-cli` (password-safe `fs_cli` wrapper). |
| named volumes `freeswitch-log`, `freeswitch-db` | Runtime logs and sqlite state. |

FreeSWITCH has no built-in env-var → config mapping. `conf/vars.xml` uses the XML preprocessor
(`exec-set esl_password=cat /run/secrets/esl_password`) and `event_socket.conf.xml` references
`$${esl_password}`. The password is not in the container's environment, in `docker inspect`, or in
any process argument.

To rotate: delete `secrets/esl_password`, run `scripts/lab-up.sh` (regenerates it), then
`docker compose up -d --force-recreate`. A password left in `.env` by milestone 1 is migrated into
`secrets/` and removed from `.env` automatically.

## Logs

```bash
docker compose logs -f freeswitch          # console log (stdout)
docker compose exec freeswitch tail -f /usr/local/freeswitch/log/freeswitch.log   # file log (debug level)
```

## `fs_cli`

`fs-cli` (a wrapper around `fs_cli`) reads the password from the secret file and passes it to
`fs_cli` through a private temporary config file that is removed on exit, so it never appears in
`argv`:

```bash
docker compose exec freeswitch fs-cli                    # interactive
docker compose exec freeswitch fs-cli -x "status"        # one command
```

Do **not** use `fs_cli -p <password>`; that puts the secret in the process list.

## ESL: where a future monitoring client connects

| Client location | Host | Port | Password |
|---|---|---|---|
| Container on the lab network (`datadog-freeswitch_lab`) | `freeswitch` (service-name DNS) | `8021` | contents of `secrets/esl_password` |
| Same container (loopback) | `127.0.0.1` | `8021` | same |
| Docker host | **not published** | – | – |

Security decisions:
- Port 8021 is **not** published to the host. Reach it from the host with `docker compose exec`,
  or attach the future agent/monitor container to the `lab` network.
- Inside the container ESL listens on `0.0.0.0` (required for other containers) but is guarded by
  the `esl_lab` ACL (`default="deny"`; allows `127.0.0.1/32` and `LAB_SUBNET`, default `172.29.77.0/24`).
- The password is a generated 48-hex-character secret; the stock default is never used.
- The health check is `esl-check --expect UP`: stdlib Python, 4 s overall deadline, authenticates over ESL, runs `api status`,
  and reports failures with fixed messages that never include the password. Exit codes: 0 ok, 1 command/health failure,
  2 auth rejected, 3 connect/timeout, 4 usage/config.

Manual ESL check from a second container on the lab network:

```bash
docker compose run --rm --no-deps --entrypoint esl-check freeswitch --host freeswitch --expect UP
```

## Ports

| Port | Proto | Published on host | Why |
|---|---|---|---|
| 5060 | UDP, TCP | `${HOST_BIND_ADDR:-127.0.0.1}:5060` | SIP (internal profile) for later call tests |
| 16384–16483 | UDP | `${HOST_BIND_ADDR:-127.0.0.1}:16384-16483` | RTP, narrowed to 100 ports (≈50 legs). Set in `switch.conf.xml`; keep in sync with the mapping in `docker-compose.yml` |
| 8021 | TCP | no | ESL, private network only |

Bridge networking with explicit mappings is used; host networking is not required. Everything
published is bound to `127.0.0.1` by default. Setting `HOST_BIND_ADDR=0.0.0.0` exposes SIP/RTP
on all host interfaces; don't do this on an internet-facing host.

The SIP profile challenges every inbound INVITE (`auth-calls=true`), registration is disabled and
the user directory is empty, so no external party can place calls. There are no default
extension passwords.

## Local test dialplan (no carrier)

`conf/dialplan/default.xml` defines two local-only extensions in the `default` context:
`9197` (answer, play a 2 s 440 Hz tone, hang up) and `9198` (answer, sleep 10 s, hang up).
Nothing is called automatically at startup. One manual call:

```bash
docker compose exec freeswitch fs-cli -x "originate loopback/9197/default &echo"
```

`scripts/verify-lab.sh --call-test` does exactly this once.

## Preparing for the synthetic-call milestone

Needed later, not built now: (1) a controlled generator (SIPp container on the `lab` network, or
ESL `originate` driven by script) with an explicit rate/duration/concurrency cap; (2) SIP users or
an ACL-based inbound path so external generators are accepted (the directory is empty today);
(3) `ext-rtp-ip`/`ext-sip-ip` if media must cross the Docker NAT to a host SIP client; (4) possibly a
larger RTP range (update both `switch.conf.xml` and the compose mapping) and higher
`max-sessions`/`sessions-per-second` (currently 200/30); (5) a `docker stats`/ESL baseline method.

## Troubleshooting

- **`secrets/esl_password` bind-mount error on `docker compose up`** – run `scripts/lab-up.sh`, which creates it.
- **Container unhealthy** – `docker compose logs freeswitch`; the healthcheck runs `esl-check` over loopback.
  ``docker compose exec freeswitch esl-check` distinguishes the cases by exit code (2 = auth rejected, 3 = unreachable/timeout).
- **Subnet conflict on `docker compose up`** – set another `LAB_SUBNET` in `.env` (the ESL ACL follows it).
- **Port 5060 in use** – stop the local SIP service, or change the host side of the mapping in `docker-compose.yml`.
- **Config changes not applied** – `docker compose restart freeswitch`, or `fs-cli -x reloadxml`.
- **Docker Desktop on macOS** – works for ESL/CLI. Host-originated RTP through Docker's VM NAT is not a goal of this milestone.

## Known limitations / not verified

- Built and tested only on **linux/arm64** (Docker Desktop on Apple silicon). amd64 uses the same
  Dockerfile but was **not built or run**. A native Linux host was **not tested**.
- SIP/RTP from an external SIP client or any real media path was **not tested**; only loopback
  calls inside FreeSWITCH were.
- The ESL ACL rejecting clients from outside the lab subnet was **not tested** (it is configured; only
  allowed-path and wrong-password cases were exercised).
- Base image is not digest-pinned; sofia-sip/spandsp are pinned by commit, FreeSWITCH by SHA-256.
- FreeSWITCH 1.11.x exists (1.11.3 at time of writing); 1.10.12 was chosen as the long-lived stable
  line. Bumping is `FS_VERSION`/`FS_SHA256` build args plus a rebuild and re-verify.
- **Residual secret exposure** (the lab is not hardened against a privileged local user):
  - The secret file is a bind mount of `secrets/esl_password`, mode 0644 inside a 0700 directory so the container's uid 999 can read it.
    Root and members of the `docker` group on the host can read it, and so can anything inside the container running as uid 999 or root.
  - Docker-level inspection (`docker inspect`, `docker top`, `/proc/*/cmdline`, `/proc/*/environ`) does not show it (verified).
  - Once FreeSWITCH loads it, the value is a global variable: any *authenticated* ESL client could read it with `global_getvar`
    or `xml_locate`. FreeSWITCH also keeps it in memory.
  - `esl-check` and `fs-cli` hold it in process memory (and `fs-cli` briefly in a 0600 temp file in a 0700 dir under `/tmp`).
  - A wrong-password probe uses `docker compose exec -e LAB_BAD_PW=wrong-password`; that is a throwaway test value, not the real secret.
  - Do not copy `secrets/` into images, backups, CI logs or chat. `.dockerignore` excludes it from build contexts.
  - The Python in the image is `python3-minimal` (about 11 MB), added only for `esl-check`.
- `sofia`'s `${local_ip_v4}` is the container IP; remote SDP will advertise it.
- Module set is minimal (no codecs beyond core PCMU/PCMA, no voicemail/conference/etc).
